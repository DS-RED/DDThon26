# 4인 AI 협업 개발 역할 분담 가이드

> **질문**: "4명에서 각각 AI를 사용해서 작업할 예정인데, 개발 역할 영역 구분을 어떻게 하면 좋을지 알려줘."
> **전제 스택**: React SPA(프론트) + Node.js(백엔드) + SQLite + SSE, 로컬 실행, 소규모 MVP/데모
> **작성일**: 2026-09-07

---

## 결론 (권장안)

4인이 **각자 AI로 병렬 작업**하는 상황에서는, 서로 대기(blocking)하지 않고 충돌을 최소화하는 것이 핵심입니다. 이 프로젝트에는 아래 **혼합형(계약 우선 + 수직 슬라이스)** 을 권장합니다.

- **먼저 4명이 함께 "공유 계약"을 30~60분 확정** → 이후 각자 독립 개발
- 공유 계약 = ① REST API 명세(엔드포인트/요청·응답 스키마) ② DB 스키마 ③ SSE 이벤트 포맷 ④ 인증 토큰 규약

계약만 고정되면, 아래 4개 영역은 서로 거의 독립적으로 진행할 수 있습니다.

---

## 권장 역할 분담 (Option A — 도메인/앱 기준, 권장)

| # | 역할 | 담당 범위 | 주요 산출물 |
|---|------|-----------|-------------|
| **P1** | **백엔드 · 주문/세션 도메인** | 인증(JWT, bcrypt), 테이블 세션 라이프사이클(시작~이용완료→이력 이동), 주문 생성/삭제/조회, 주문 이력, **SSE 발행(publisher)** | 인증·주문·세션 API, SSE 스트림 |
| **P2** | **백엔드 · 메뉴/매장 도메인 + 데이터·공통 인프라** | 메뉴 CRUD·노출순서, 매장/카테고리, **SQLite 스키마·마이그레이션·시드 데이터**, 공통 미들웨어(에러/검증/로깅), 서버 부트스트랩 | 메뉴·매장 API, DB 스키마, seed 스크립트, 서버 골격 |
| **P3** | **프론트엔드 · 고객용 앱** | 자동 로그인/세션, 메뉴 조회·카테고리 탐색, 장바구니(로컬 저장), 주문 생성 플로우, 현재 세션 주문 내역 | 고객용 React 화면·상태관리·API 연동 |
| **P4** | **프론트엔드 · 관리자용 앱** | 매장 로그인 UI, **실시간 모니터링 대시보드(SSE 구독)**, 테이블 관리(초기설정·주문삭제·세션 종료·과거내역), 메뉴 관리 화면 | 관리자용 React 화면·SSE 클라이언트·API 연동 |

**이 분할의 장점**
- 프론트 2명 / 백엔드 2명으로 스택 전문성 집중 → AI 프롬프트 컨텍스트가 좁고 일관됨
- P1(주문/세션)이 SSE **발행**, P4(관리자)가 SSE **구독** → 둘이 이벤트 포맷만 합의하면 됨
- P2가 DB·시드·서버 골격을 초기에 깔아두면 P1이 그 위에서 작업(초기 1일만 순서 의존, 이후 병렬)

**주의(의존성)**
- 초기 순서: **P2(스키마·서버 골격) → P1(도메인 로직)** 이 살짝 앞섬. P2가 스키마+빈 서버를 1일 차에 먼저 커밋하면 병목 해소.
- 프론트(P3/P4)는 계약 확정 후 **목(mock) API**로 즉시 병렬 시작 가능.

## 대안 (Option B — 기능 수직 슬라이스)

각자 "한 기능을 프론트+백엔드까지 통째로" 담당:

| # | 수직 슬라이스 |
|---|----------------|
| P1 | 인증 + 테이블 세션 (관리자 로그인, 태블릿 자동 로그인, 세션 시작/종료) |
| P2 | 메뉴 (메뉴 관리 CRUD + 고객 메뉴 조회/탐색) |
| P3 | 주문 (장바구니 + 주문 생성 + 현재 세션 주문 내역) |
| P4 | 실시간 모니터링 대시보드 (SSE + 관리자 주문 관리 + 과거 내역) |

- **장점**: 각자 기능 하나를 end-to-end 소유 → 책임 명확, 데모 단위로 완결
- **단점**: 4명 모두 프론트·백엔드·DB를 다 만져 **공유 파일 충돌↑**, 스택 컨텍스트 스위칭 비용↑ (AI 사용 시 프롬프트가 넓어짐)
- **적합 상황**: 팀원 모두 풀스택에 익숙하고, 기능별 데모를 빠르게 뽑고 싶을 때

> 소규모 MVP + "각자 AI 사용" 조건에서는 컨텍스트가 좁아 프롬프트 품질이 높은 **Option A를 우선 권장**합니다.

## 공유 계약 (4명이 먼저 합의할 것)

1. **API 명세**: 엔드포인트 경로, 메서드, 요청/응답 JSON 스키마, 에러 포맷, 상태 코드
   - 예: `POST /api/orders`, `GET /api/orders?sessionId=`, `POST /api/admin/login`, `GET /api/stream/orders`(SSE)
2. **DB 스키마**: Store, Table, TableSession, Menu, Category, Order, OrderItem, OrderHistory, AdminUser (P2가 초안 → 전원 리뷰)
3. **SSE 이벤트 포맷**: 이벤트명(`order.created`, `order.updated`, `order.deleted`, `session.closed`)과 payload 스키마
4. **인증 규약**: JWT 클레임 구조, 16시간 만료, 헤더 형식(`Authorization: Bearer`)
5. **Git 워크플로우**: 브랜치 전략(예: `feat/<area>-<name>`), PR 리뷰 규칙, 메인 브랜치 보호

## 협업 운영 팁 (AI 병렬 작업 특화)

- **폴더로 소유권 분리**: 예) `server/src/orders/`(P1), `server/src/menu/` + `server/src/db/`(P2), `client-customer/`(P3), `client-admin/`(P4). 파일 충돌을 구조적으로 예방.
- **API 계약을 코드로 고정**: OpenAPI(swagger) 또는 공유 타입 정의를 리포에 두고 프론트/백이 같은 소스를 참조 → AI가 스키마를 정확히 따르게 유도.
- **목(mock) 우선**: 프론트는 백엔드 완성 전 mock 서버/고정 JSON으로 시작.
- **작은 PR·잦은 병합**: 각자 AI가 큰 덩어리를 만들기 쉬우므로, 계약 변경은 즉시 공유하고 매일 병합.
- **통합 담당 로테이션**: 매일 1명이 전체 로컬 실행(시드→고객 주문→관리자 실시간 확인)으로 통합 스모크 테스트.

## AI-DLC 워크플로우와의 연계

이 역할 분담은 **참고용 사전 계획**입니다. AI-DLC 워크플로우가 진행되면 **Units Generation** 단계에서 시스템이 "작업 단위(units)"로 정식 분해되며, 위 P1~P4 영역과 자연스럽게 대응될 수 있습니다. 실제 담당 배정은 Units Generation 산출물(`unit-of-work.md`, `unit-of-work-dependency.md`)을 확정한 뒤 그 단위에 맞춰 최종 조정하시길 권장합니다.

# 실행 계획 — P3 고객 앱 착수

작성일: 2026-09-07 · 기준 코드: `a7cf83a` · 상태: **APPROVED — 2026-09-07, P3 구현 진행 / 일부 인수 조건 미완료**

이 계획은 이미 승인된 요구사항을 재사용하고, P3의 설계 및 코드 생성 순서를 정의한다. P1/P2 과거 단계의 누락된 승인을 소급 생성하지 않는다. 이번 사용자 입력 “구래 진행해”는 리뷰에서 제안한 P3 설계·계획 작성의 진행 승인으로 기록하며, 아직 작성되지 않았던 코드 생성 계획의 승인으로 간주하지 않는다.

## 1. 현재 시스템과 변경 영향

- 프로젝트는 Greenfield로 시작했으며 현재 Express/SQLite 백엔드가 존재한다. 이번 변경은 기존 백엔드에 고객 React SPA를 추가하는 작업이다.
- P1: 인증, 주문, 착석 세션, 테이블 관리, SSE. P2가 임시 구현했으며 P1 인수 검토 대상이다.
- P2: 메뉴/매장, DB, 시드, 공통 서버, CORS, 판매 가능 메뉴 필터.
- P3: `client-customer/` 신규. FR-C1~C5 및 고객 흐름만 소유한다.
- P4: `client-admin/` 신규 예정. 관리자 화면, SSE 구독은 P4 소유다.
- DB 변경 없음. 기본 구현은 현재 API를 소비한다. 착석 세션 식별 보강은 P1 소유의 별도 의존사항이다.
- 영향: 고객 UI, 브라우저 저장 상태, 인증 만료 복구, 주문 오류 처리, 접근성.
- 위험도: 중간. 주문 중복과 다른 고객의 장바구니 잔존이 핵심 위험이다. P3 파일 단위로 되돌릴 수 있으며 DB 롤백은 없다.

## 2. 단계별 실행 결정

P2의 과거 Lean 선택을 팀 전체의 영구 생략 승인으로 확대하지 않는다. 아래는 P3에 적용할 단계 및 깊이의 제안이며, 세부 설계/계획 초안을 함께 검토한다. 단계별 완료와 승인 기록은 구분한다.

| 단계 | 결정 | 깊이 및 근거 |
|---|---|---|
| Workspace Detection | 재확인 완료 | 기존 백엔드와 미추적 P3 문서 2개 확인 |
| Reverse Engineering | 제한적 실행 | 기존 API·폴더·의존성 검토를 이 계획 및 설계의 API 표에 기록. 전사 아키텍처 재설계 없음 |
| Requirements Analysis | 승인본 재사용 | FR-C1~C5를 인수 조건에 매핑. 원 문서의 성공 화면 5초 요구 포함 |
| User Stories | 실행 | 고객/초기 설정 담당자 관점의 5개 시나리오와 인수 조건을 설계 초안에 작성 |
| Workflow Planning | 필수 실행 | 이 문서. 실행·생략 사유, 팀 의존성, 승인·검증 게이트 정의 |
| Application Design / Units Generation | 실행 | P3 단위 경계, 컴포넌트, P1/P2 의존성 정의. 아래 단위 표 및 설계 초안에 통합 작성 |
| Functional Design | 실행 | 인증/장바구니/주문 상태 전이와 예외 시나리오 정의 |
| NFR Requirements / Design | 실행 | 기존 요구를 P3 접근성·저장·에러·테스트 설계에 구체화 |
| Infrastructure Design | SKIP 제안 | 로컬 SPA와 기존 서버 사용. 클라우드/컨테이너 변경 없음 |
| Code Generation | 필수 실행 예정 | 별도 10단계 계획 승인 후 구현 |
| Build and Test | 필수 실행 예정 | P3 단위·컴포넌트·실 API 통합·브라우저 시나리오 검증 |
| Operations | PLACEHOLDER | 배포 요청 없음. 로컬 실행 안내는 P3 README에 포함 |

별도 단계별 산출물로 확장할 경우 기존 초안을 원본으로 분리하며 승인되지 않은 초안을 완료 처리하지 않는다. 이번에는 작은 고객 앱의 검토 부담을 줄이기 위해 스토리·단위·설계 초안을 [P3 설계](../../construction/p3-customer-app/design.md)에 통합한 방식을 제안한다. 이는 상세 규칙의 개별 파일 템플릿을 그대로 모두 생성한 상태는 아니다.

텍스트 실행 흐름: 기존 요구사항/코드 재확인 → P3 실행 계획·스토리·설계 검토 → 코드 생성 계획 승인 → 10단계 구현 → 빌드/테스트 → 결과 검토. Mermaid 도구 없이도 검토 가능한 텍스트 표현을 사용한다.

## 3. 단위 및 의존성

| 단위 | 소유 경로/책임 | P3 의존 |
|---|---|---|
| p2-backend-menu-store | `server/src/menu/`, `store/`, `db/`, 서버 공통 기반 | 매장/메뉴 GET, CORS, 데모 시드 |
| p1-backend-orders-sessions | 인증/주문/세션/테이블/SSE 서버 모듈 | 테이블 로그인, 주문 POST, 현재 주문 GET, 세션 식별 계약 검토 |
| p3-customer-app | `client-customer/` 및 P3 AI-DLC 문서 | FR-C1~C5, 고객 UI·로컬 상태·API 소비 |
| p4-admin-app | `client-admin/` | 세션 종료 통합 시연 시 협업. P3 단독 개발의 선행조건은 아님 |

공유 파일 변경은 계약 변경과 P3 문서 갱신을 구분한다. P3 코드 생성 범위에 백엔드 수정은 포함하지 않는다. 기존 문서의 “client-customer 밖 수정 금지”는 앱 코드 소유권 규칙으로 해석하고, 사용자가 요청한 AI-DLC 계획·상태 문서 정리는 허용 범위로 기록한다.

개발 순서: P2 기반(존재) → P1 API(존재, 임시) → P3 실제 API 연동. P4는 독립 진행 가능하다. 세션 보강 대기 중에도 메뉴·장바구니·로그인·주문 화면 구현은 가능하나, 세션 전환 인수 조건은 검증 전까지 미완료로 유지한다.

## 4. 계약 기준과 기존 P3 초안

현재 계약은 `docs/contracts/api-auth-orders-sessions.md`, `api-menu-store.md`, `shared-conventions.md`다. 최신 코드와 계약의 차이는 [설계의 계약 정리](../../construction/p3-customer-app/design.md)에 기록한다.

착수 시 존재하던 `docs/contracts/p3-customer-app.md`, `p3-requests-to-p1-orders-auth.md`는 원문 보존한다. 해당 파일의 “인증/주문 계약 없음”, `api-orders.md` 예상 파일명, 제안 로그인/내역 URL은 과거 초안이며 현 구현 계약으로 사용하지 않는다. 품절 표시와 페이지네이션 등 유효한 P3 제안은 새 설계에 반영한다. 팀원에게 메시지를 발송한 상태는 아니다.

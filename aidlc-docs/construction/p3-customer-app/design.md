## 2. 앱 구조와 화면

기술: 승인된 Vite + React SPA. JS/ESM, 브라우저 fetch, React Context + reducer로 시작한다. 테스트는 Vitest/React Testing Library 및 Playwright를 사용하며 버전은 구현 시 호환성을 확인하고 잠금 파일로 고정한다.

| 경로/컴포넌트 | 화면·상태 | 책임 |
|---|---|---|
| `/setup` / SetupPage | 매장 코드, 테이블 번호, 비밀번호, 인증 중/실패 | 태블릿 최초 설정·재인증 실패 복구 |
| `/` / MenuPage | 매장명, 테이블 번호, 카테고리, 메뉴 카드, 상세 다이얼로그 | 메뉴 기본 화면, 담기, 장바구니/주문 내역 진입 |
| `/cart` / CartPage | 항목, 수량, 합계, 품절·가격 변경 표시 | 카트 편집, 최종 주문 확인 |
| `/order-success` / OrderSuccessPage | 서버 주문 ID, 최종 금액, 남은 시간 | 카트 비운 후 5초 표시, 즉시 메뉴 이동 버튼, 타이머 정리 |
| `/orders` / OrdersPage | 로딩/오류/빈 목록/페이지/주문 상세 | `/mine` 조회, 명시적 새로고침, 재진입 및 포커스 복귀 시 갱신 |
| AppShell | 상단 매장·테이블, 이동 메뉴 | 공통 탐색과 오류 안내 |

- AuthProvider: `bootstrapping → setup | authenticating → ready | authError`. 활성 table/store는 로그인 응답에서 결정한다.
- CartProvider: `items`, `storeId`, `tableId`, `sessionMarker`, `version`. 합계는 파생값이다.
- Checkout: `idle → validating → submitting → success | rejected | unknown`. rejected/unknown에서는 저장 카트를 유지한다.
- `api/`는 원격 데이터와 HTTP 오류를 처리한다. `storage/`는 직렬화/검증/버전 관리, `utils/`는 원화·날짜 변환을 담당한다.
- 접근 가능한 label, heading, dialog 포커스, 오류 안내 영역, 키보드 조작과 고정 `data-testid`를 제공한다. 백엔드/디버그 용어를 고객 화면에 노출하지 않는다.
- 태블릿 가로 화면을 기본으로 작은 화면에서는 단일 열로 전환한다. 카테고리·장바구니 접근을 유지한다.

## 3. 실제 API 계약

Base URL은 `VITE_API_BASE_URL`, 기본 로컬 개발 주소는 `http://localhost:3000`으로 설정한다. API 경로를 한 어댑터에 모으고 CORS 허용 오리진을 README에 기록한다.

| 기능 | API / 데이터 |
|---|---|
| 인증 | `POST /api/auth/table/login`, body `{storeCode, tableNumber, password}`, 응답 `{token, table:{id, storeId, tableNumber}}` |
| 매장 표시 | `GET /api/stores/:storeId` |
| 메뉴 | `GET /api/stores/:storeId/menu`, 응답 `[{category, items}]` |
| 주문 | `POST /api/stores/:storeId/orders`, table Bearer 토큰, body `{items:[{menu_item_id, quantity}]}` |
| 내역 | `GET /api/stores/:storeId/orders/mine`, table Bearer 토큰, 배열 응답 및 각 주문의 `items` 사용 |

- 숫자 `storeId`/`tableId`는 로그인 응답을 사용한다. `storeCode` 문자열과 혼동하지 않는다.
- 주문 표시 번호는 응답 `id`를 `주문 #123`으로 표시한다. 존재하지 않는 `order_number`를 요구하거나 생성하지 않는다.
- 단가/이름/총액/착석 세션은 서버가 결정한다. 주문 body에 `table_id`, `session_id`, 가격을 추가하지 않는다.
- 주문 상태: `pending → 대기중`, `preparing → 준비중`, `completed → 완료`. 프론트는 서버 상태를 표시하며 변경 API를 호출하지 않는다.
- UTC `YYYY-MM-DD HH:MM:SS`를 명시적으로 UTC ISO 형태로 변환해 브라우저에서 지역 시각으로 표시한다. 원문을 로컬 시각으로 해석하지 않는다.
- 메뉴의 `category:null`은 기타로 마지막에 표시한다. 서버의 분류/메뉴 순서를 유지한다.
- 기존 P3 초안의 품절 표시 결정을 유지하기 위해 메뉴는 필터 없이 호출하고 품절 카드를 비활성화한다. 신규 `?available=true`는 지원되지만, 이를 사용하면 품절 카드를 표시할 수 없으므로 기본 호출에는 넣지 않는다.
- `/orders/:orderId`, `/tables`, `/events`는 관리자용이다. P3 코드에는 관리자 토큰 및 관리자 API 호출을 넣지 않는다.
- `api-menu-store.md` 상단의 placeholder 설명은 오래된 문구이며 실제 미들웨어는 인증을 수행한다. P3가 의존하는 메뉴 조회는 공개다.

## 4. 인증과 저장

- 전용 로컬 데모 태블릿 요구사항에 따라 최초 성공한 설정 `{storeCode, tableNumber, password}`와 토큰/테이블 정보를 브라우저에 저장한다. 비밀번호는 로그·URL·오류 상세에 기록하지 않는다. 이 저장 정책은 원 요구의 자동 로그인을 위한 설계 선택이며 운영용 인증 설계 승인을 의미하지 않는다.
- 기동 시 저장값을 검증한다. 유효 토큰을 재사용하고 GET 요청의 401 또는 만료 감지 시 저장 설정으로 한 번 재로그인한다. 동시에 발생한 재인증은 하나로 합친다.
- GET은 인증 복구 후 한 번 재조회 가능하다. 주문 POST는 재인증 이후에도 사용자 재확인을 거친다. 무한 로그인 재시도는 하지 않는다.
- 저장 키: `table-order:customer:setup:v1`, `cart:{storeId}:{tableId}`. 카트 값은 버전·세션 표식·항목을 포함한다. 기존 제안 키를 유지하고 실제 이전 데이터가 있으면 검증 후 복원한다.
- 저장 차단/용량/JSON 오류는 앱 크래시로 이어지지 않게 처리한다. 저장 불가 시 새로고침 유지가 안 된다는 화면 안내를 제공한다.
- 매장/테이블 설정 변경 시 해당 카트와 메모리 내 주문 캐시를 분리/초기화하고 진행 중 요청을 취소한다. 늦게 도착한 이전 테이블 응답은 반영하지 않는다.

## 5. 장바구니와 주문 실패 규칙

- 메뉴 ID 기준으로 항목을 합치고 수량은 1~999로 제한한다. 1에서 감소하면 삭제한다. 가격은 원화 정수로 계산한다.
- 저장 카트는 표시용 스냅샷이며 주문 확정 직전에 메뉴를 재조회한다. 사라지거나 품절된 항목은 삭제/수정 안내와 함께 주문을 막고 카트를 보존한다. 가격이 바뀌면 새 합계를 표시하고 다시 확인받는다.
- 제출 중 수량 변경·추가 제출을 막는다. 성공 201을 받은 경우에만 카트를 비우고 서버 응답을 성공 화면에 표시한다.
- HTTP 400/401 등 명확한 거절은 카트를 유지하고 수정/재인증을 안내한다.
- 타임아웃/연결 단절/5xx는 주문 반영 여부가 불명확할 수 있다. `unknown`으로 두고 현재 주문 확인을 안내한다. 자동 POST 재전송이나 내용 유사성만으로 성공 판정하지 않는다.
- 서버 멱등성 키 계약은 현재 없다. 클라이언트의 중복 클릭 방지만으로 네트워크 재시도 중복까지 해결됐다고 주장하지 않는다. 해당 상황은 통합 검증·잔여 제약에 기록한다.

## 6. 착석 세션 전환 — P1 의존사항

인증 JWT(16시간)와 착석 세션(첫 주문~이용 완료)은 다르다. 토큰 만료를 이용 완료로 취급하지 않는다. 주문 POST와 `/mine`의 주문에는 `session_id`가 있지만, 빈 `/mine` 배열로는 다음 두 경우를 구분할 수 없다.

1. 아직 첫 주문 전이거나 이용 완료된 테이블.
2. 착석 세션은 활성이나 관리자가 모든 주문을 삭제한 테이블.

따라서 빈 목록만 보고 카트를 비우는 로직은 사용하지 않는다. `/mine`은 조회 시점의 현재 주문을 필터링하므로 내역 표시에는 사용할 수 있지만, 카트의 세션 전환 자동 초기화 보장에는 추가 정보가 필요하다.

**P1 검토 요청 초안:** table 토큰으로 현재 `{sessionId: number|null, status: active|none}`를 읽는 계약(기존 응답 확장 또는 별도 GET)을 확정한다. 경로를 P3가 임의로 정해 실제 호출하지 않는다. 확정되면 앱 진입·포커스 복귀·주문 전 및 활성 화면에서 주기적으로 확인하고, 알려진 활성 세션이 닫히거나 다른 ID로 바뀌면 이전 카트/주문 캐시를 초기화한다. 첫 주문에서 none→active로 바뀌는 정상 전환은 다른 고객으로 오인하지 않는다.

현재 API만 사용하는 기본 화면 개발은 진행 가능하다. 하지만 “이용 완료 후 남은 로컬 카트 자동 초기화” 인수 조건은 계약 및 통합 검증 전까지 **미완료**다. 수동 초기화로 요구사항을 충족했다고 표시하지 않는다. 세션 확인 주기와 확인-주문 사이 경쟁 상태 처리도 P1 계약에서 검토한다.

## 7. 검증 시나리오

| 구분 | 검증 |
|---|---|
| 단위 | 카트 합치기/상한/삭제/원화 합계, 손상 저장값, 매장·테이블 분리, UTC 변환 |
| 컴포넌트 | 로그인 오류/복구, 품절 비활성화, 메뉴 빈 상태, 페이지 이동, 오류 재시도, 5초 타이머 정리 |
| 주문 통합 | 요청 스키마, 서버 가격 표시, 201 시 초기화, 400 시 유지, 제출 중 클릭 차단, 응답 유실 시 자동 재전송 없음 |
| 인증 통합 | 만료 시 한 번 재인증, 실패 시 설정 복귀, 이전 테이블 지연 응답 무시 |
| 브라우저 | 최초 설정→메뉴→카트→새로고침 유지→주문→5초 복귀→내역. 태블릿·작은 화면·키보드 점검 |
| 세션 통합 | 관리자 종료 후 현재 주문 제외, 새 주문의 새 세션, 활성 세션 내 주문 전부 삭제와 이용 완료 구별, 다른 고객 카트 초기화 |

로컬 전용 테스트 데이터베이스를 사용한다. 관리자 동작은 테스트 픽스처에서만 수행한다. P3 고객 코드에 관리자 자격증명을 포함하지 않는다. 확정되지 않은 API는 목으로만 검증하고 실제 통합 통과와 구분한다.
